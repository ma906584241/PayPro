# 线上支付后仍停留扫码界面：排查记录

核查日期：2026-10-28。网站：https://pay.aioperis.com 。用户确认已重新部署；二维码由用户自行调整，本次不修改二维码及其选择逻辑。

## 已确认的原因

线上存在前后端版本不一致：

| 只读检查 | 实际结果 |
| --- | --- |
| `/recharge.html` | 已在跳转链接携带 `paymentConfirmToken` |
| `/assets/js/api-config.js` | 已定义 `/order/confirm-paid` |
| `/order/payment-confirmation?orderId=__paypro_readonly_deployment_check__` | 返回业务 code 404、“订单不存在”；确认路由已经生效，未创建或修改订单 |
| `/payment.html` | 没有“我已完成付款”、没有 `paymentConfirmToken`，仍使用固定300秒倒计时及旧状态轮询 |
| `/payment` | 同样没有付款确认入口 |

检查使用额外时间戳查询参数及 `Cache-Control: no-cache`，请求由 nginx 返回 HTTP 200。首次核查确认了旧模板响应；随后用户提供实际部署细节，进一步锁定了宿主机覆盖层。

客户实际扫码付款不会让个人收款码主动回调当前项目。新流程需要客户按钮提交声明，然后管理员核实到账并批准。旧模板没有声明入口，因此即使后端已更新，客户也无法发起通知；付款页只能继续等待状态变化。

## 修复范围

将当前部署实际加载的 `payment.html` 合并到新确认流程，保留用户自行调整的二维码资源及 `createPaymentOrder` 中的选择逻辑。不要直接拿旧支付页整文件覆盖新版，也不要要求客户重新付款。

新版模板须同时具备：

- URL读取 `paymentConfirmToken`。
- `GET /order/payment-confirmation`，凭证放请求头，查询不发信。
- “我已完成付款”按钮及二次确认；只有确认后才POST。
- 已声明后显示“等待管理员核实到账”，停止付款倒计时，继续查询审核状态。
- 通知失败可重试；缺失凭证的旧链接提示按原审核流程处理。

仓库中的[支付模板](../../src/main/resources/templates/payment.html)已经包含上述机制。线上二维码调整若只涉及 `qr` 文件，部署时保留外置 `qr` 目录即可；若同时调整了模板，需要保留二维码相关变更后合并确认机制。

## 已确认的加载来源

用户提供的现网部署信息：

- Docker Compose在 `/opt/paypro` 本机构建 `pay:latest`；Nginx反代本机 `127.0.0.1:8889`。
- `config` 挂载到容器 `/app/appsystems/config`，`qr` 挂载到 `/app/appsystems/qr`。
- 实际模板是 `/opt/paypro/config/templates/payment.html`，不是新镜像内置模板。用户核对的宿主/容器MD5前缀均为 `de76414e…`，mtime为当天14:44。
- 每次部署会从aside/备份恢复旧覆盖层，导致它持续优先于新版模板。二维码调整只涉及 `qr` 图片文件，不是这次旧模板的来源。

因此，仅重新构建镜像或刷新浏览器不能解决该问题，必须升级这个挂载文件。

## 本次修复工具

新增 [upgrade_payment_template.py](../../scripts/upgrade_payment_template.py)，仅依赖Python3标准库。它从仓库新版支付模板读取确认流程，再合并到实际覆盖文件：

- 保留覆盖文件的HTML内容、品牌、二维码HTML、已有样式。
- 原样保留 `createPaymentOrder` 和 `generateQRCode` 代码块（统一换行符），因此 `fallbackToRemark` 优先、自定义码路径、金额目录、支付宝唤起链接及canvas配置保持原有行为。
- 升级Vue的声明状态、凭证读取、鉴权轮询、二次确认与重试逻辑，补入确认区域、相关样式、可信数据加载前的二维码隐藏条件和正确倒计时条件。
- 替换前将原始字节完整备份到 `config/template-backups/payment-时间戳-哈希.html`，随后原子替换目标；重复运行不重复添加按钮或备份。
- 如存在未知自定义组件方法、数据字段、组件选项、无法识别的布局或二维码可见性条件，停止并提示手动合并，原文件不变。工具不访问支付、邮件、数据库、Redis或远程服务。

脚本升级的是组件状态和确认流程，不是通用HTML三方合并工具。未知自定义数据和计算属性会停止自动升级，应先人工审阅；已知现网覆盖层结构已通过下载页面验证，原始挂载文件仍会在执行前单独校验。

## 日常部署：启动时自动处理（推荐）

现在已将升级流程接入根Dockerfile及 `start.sh`。首次拉取包含本次改动的代码并重新构建应用镜像后，日常仍使用原来的Compose部署命令：

```bash
cd /opt/paypro
# 在启动应用前完成现有aside/备份恢复步骤
# 代码同步后重新构建并启动应用
docker compose up -d --build --no-deps pay
docker compose logs --tail 80 pay
```

该命令假定现网MySQL/Redis已在运行，沿用用户的既有服务；首次安装仍使用项目完整Compose启动流程。无需再手动执行Python脚本，也不要求宿主机安装Python。

启动顺序：

1. Docker完成 `config`、`qr` 目录挂载。
2. `start.sh` 在启动Java之前检测外置 `config/templates/payment.html`。
3. 有覆盖文件：调用镜像内的 `prepare_payment_template.sh`，按需备份并升级；已经是当前流程则不写文件、不生成新备份。没有覆盖文件：使用JAR内置模板，不生成覆盖层。
4. 成功后才启动Java。无法识别的自定义结构、只读或无权限写入等错误会保留原文件并阻止本次启动，日志给出原因，不继续使用缺失确认入口的旧流程。

新版源模板及工具固定打包在镜像 `/app/payment-template`，位于 `config` 挂载目录之外，aside恢复操作不会遮挡它们。运行镜像通过Debian包安装Python3，Python仅用于启动前处理覆盖层；原网站运行仍为Java8。

每次部署即使重新恢复了旧aside文件，只要恢复发生在容器启动之前，新容器就会再次自动升级。不要在容器已经启动后再覆盖模板；如有这种部署顺序，应将恢复步骤提前。数据库、二维码、Nginx和SMTP配置均不参与该自动升级。

此自动流程针对用户正在使用的**项目根Dockerfile/Compose构建入口**。`src/main/resources/Dockerfile` 是另一个旧的预构建JAR入口，不包含新工具；不应拿它替代当前Compose的根构建入口。

## 旧镜像的手动修复方式（可选）

先将本次新增的 `scripts/upgrade_payment_template.py` 同步到服务器，并确认 `/opt/paypro/src/main/resources/templates/payment.html` 是包含确认按钮的仓库新版源模板。**不要把网上下载的已渲染HTML作为新版源模板。**

在现网已恢复原覆盖层后执行：

```bash
cd /opt/paypro
python3 scripts/upgrade_payment_template.py --apply
python3 scripts/upgrade_payment_template.py --check
# 仅在上面两步成功后重启应用；无需重建镜像
# 若现网服务名不是pay，替换为实际应用服务名
docker compose restart pay
```

默认升级的正是 `/opt/paypro/config/templates/payment.html`。`--check`只读，0表示已是当前流程，1表示仍需升级，2表示结构异常或文件访问失败。也可先生成旁路预览，不动原文件：

```bash
python3 scripts/upgrade_payment_template.py --output /tmp/paypro-payment-preview.html
```

手动方式仅用于尚未更新镜像的临时处理。更新到包含自动启动流程的新镜像后，不再需要把上述Python命令加入每次部署步骤。已经升级的覆盖文件也可作为未来恢复的新基线。

本次不修改Compose挂载、二维码目录、Nginx、SMTP或数据库，无需重复执行数据库迁移。只读验收：

```bash
curl -fsS -H 'Cache-Control: no-cache' 'http://127.0.0.1:8889/payment.html' | grep -E 'paymentConfirmToken|confirmPaid|我已完成付款'
curl -fsS -H 'Cache-Control: no-cache' "https://pay.aioperis.com/payment.html?deploymentCheck=$(date +%s)" | grep -E 'paymentConfirmToken|confirmPaid|我已完成付款'
```

若本机新版、域名旧版，再检查代理缓存和其他实例；若均旧，重新核对容器内挂载文件、脚本输出的哈希及实际模板加载路径。
